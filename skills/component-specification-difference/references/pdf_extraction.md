# Extracting tables from component specification PDFs

Everything here was learned by getting it wrong against two real documents — TMFC003 v2.0.0 (published,
Word-derived) and v3.1.0 (generated by `component-specification-markdown` via xhtml2pdf). The two
generations fail in *different* ways, which is why the extractor mixes strategies rather than picking one.

Read this before changing `extract_spec_pdf.py`.

## Locate sections by heading text, never by number

Successive generations number the same content differently. v2.0.0 numbers Exposed APIs 3.1; v3.1.0 adds
an API context diagram and numbers Exposed APIs 3.1 with Dependent 3.2 — and an intermediate Confluence
export drops literal numbers from the text entirely, letting Word's Heading styles number them. Matching
`"Exposed APIs"` survives all three. Matching `"3.1"` silently compares the wrong sections and produces a
confidently wrong report.

## Blocks are not in reading order

`page.get_text("blocks")` returns blocks in creation order, not top-to-bottom. A table's text can arrive
*before* the heading that introduces it, so a naive "track the current heading as I walk the blocks" loop
attributes that table to the previous section. Sort by `(y0, x0)` first. This cost a real bug: API ids
were being credited to the wrong section, which made a present API look newly added.

Same applies when interleaving headings with tables — sort the combined list by vertical position so a
page carrying the end of one section and the start of the next assigns its tables correctly.

## A long table arrives as one fragment per page

`find_tables()` reports a table spanning five pages as five separate tables, and **only the first
fragment carries the header row**. Map columns from the header on the fragment that has one, then reuse
that mapping for the continuation fragments. Without this, a 55-row table yields 8 rows.

A continuation fragment also keeps the current section — no heading intervenes — so section tracking
needs no special case here.

## Header labels can sit in different columns than their own data

This is the one that looks impossible until you print the raw rows. In the older documents' eTOM and
Functional Framework tables, `find_tables()` reports spurious empty columns *and* puts the header label in
a different column index than the data beneath it: the FF table's `Function` header sits in column 1
while every function ID sits in column 0. Mapping header text to a column index therefore reads the wrong
cells — or empty ones.

For ID-led tables, ignore the header entirely: compact each row to its non-empty cells and assign them
positionally, anchored on the leading ID. That is what `_id_anchored()` does, and it is why eTOM and FF
extraction is exact on both documents.

Use header mapping only where the column *set* genuinely varies between versions and positional reading
couldn't tell which columns are present (the SID table gained a definition column; the API tables gained
Version and Rationales). Keep a positional fallback for when the mapping comes back empty.

## Split headers, and the substring trap

Two related traps in header detection:

- A header can span two physical rows (`Function` on one, `ID` on the next). Merge both rows before
  matching. But merge only rows that *look like headers* — pulling in the first data row lets its content
  decide the column mapping.
- Matching header marker words as plain substrings misfires on real prose. `"function id"` appears inside
  *"Orchestration function identifies Service Order Items"*, which silently dropped Functional Framework
  function 214 as though it were a header row. Match at word boundaries, and treat any row that leads with
  a valid ID as data regardless of what else it contains.

There is a third, subtler version: the *second* row of a split header (`ID` / `Level 1` / `Level 2`)
matches no marker word at all and looks exactly like a description continuation. Left unhandled it spliced
the literal text `"Level 1"` into the middle of 5 of 18 real FF descriptions. Recognise it by testing
whether every cell in the row is a short header-ish token.

## Interleaved cell text: the one that can't be fixed

When `find_tables()` mis-places a column boundary, pymupdf assembles the two neighbouring cells' text into
one string **interleaved by x position**:

| Truth | What comes back |
|---|---|
| `productOfferingPrice` + `GET, GET /id` | `productOfferingP` + `ricGeET, GET /id` |
| `resourceSpecification` + `GET, GET /id` | `resourceSpecific` + `atioGnET, GET /id` |
| `cancelResourceOrder` + `GET /id, POST` | `cancelResourceO` + `rdGeErT /id, POST` |

`ricGeET` is `rice` and `GET` merged in x order. This is not recoverable by string surgery — the two
strings overlap in x, so there's no alternation to undo and no way to know where each character came from.

Two cases *are* recoverable and worth handling, since they're common:

- **Resource and operations in one cell**, whitespace-separated (`productSpecification GET, GET /id`) —
  split on the whitespace before the first verb. Unambiguous, because resource names never contain spaces.
- **A clean glue** where the tail is contiguous (`cancelServiceOr` + `derGET, GET /id, POST`) — split the
  leading lowercase run off the verbs and give it back to the preceding partial cell.

For the genuinely interleaved rest: flag the row rather than trusting it. `_parse_api_section()` sets
`resource_confident: false`, and the comparison declines to diff resource-level detail, saying so instead
of reporting a truncated name as a change. A wrong resource name in a diff is worse than an admitted gap:
the gap costs a sentence, the wrong name costs an investigation.

## What didn't work: rebuilding from word coordinates

Reasonable-sounding idea, tried and reverted: take the table's true column boundaries from the vertical
border lines the renderer drew (`page.get_drawings()`), then re-bin `page.get_text("words")` into those
columns, folding wrapped lines into logical rows.

It did fix the truncation on the generated PDF — and it **regressed the older document badly**, turning 12
dependent-API rows into 25 spurious ones, because that document's borders don't correspond to the column
grid the same way and lines fold differently. Net worse. If you try this again, gate it per document
generation and measure both before keeping it.

## Text hygiene

- **De-hyphenate before collapsing newlines.** A word broken across lines (`pre-\norder`) must rejoin
  without a space; collapse first and you get `pre- order`, which then shows up as a difference between
  two documents that merely wrapped it in different places.
- **Framework descriptions can contain raw HTML.** Functional Framework function 205's text carries
  `&amp;` and a `<ul><li>` list rather than prose. Flatten the list to dashes, drop remaining tags and
  unescape entities — otherwise it's compared, and rendered, as literal markup.
- Normalise smart quotes, en dashes, bullets and non-breaking spaces, or they generate differences that
  are purely typographic.

## Presence as a safety net

Cell parsing can lose a row outright — the older layout packs an entire bullet list into one operations
cell, and one row's id went down with it. A lost row would then be reported as an API *newly added* in the
other version.

So alongside table parsing, harvest every `TMFnnn` id appearing in each API section's text
(`_section_api_ids()`). If an id is present in one document's section text but no row parsed for it, it is
not an addition or a removal — it's missing detail, and the report says so. This over-includes an id
merely mentioned in prose, which is the right direction to err: a suppressed true finding is recoverable
from the caveats, a fabricated one wastes someone's afternoon.

Finally, check the arithmetic closes. `retained + added` must equal the new count and
`retained + removed` the old count. When it doesn't, rows were lost — investigate before trusting the
report.
